# API 비용 없는 월간 보고서 운영 검토

검토일: 2026-09-06. 기준: `d8a2c12`와 저장소의 2026-09-04 실행 산출물(2026년 8월 보고서).

## 결론

월 1회 내부 보고서라면 기존 Codex 구독으로 로컬 프로젝트의 수집·판정·보고서 생성을 처리하는 방식이 우선이다. 사람이 브리프와 JSON을 채팅창·저장소 사이에서 옮기는 단계를 없앨 수 있다. 구독 포함 사용량 안에서는 별도 모델 API 과금 없이 운영할 수 있지만, 구독료·사용량 한도는 남는다. 이 저장소에서 전체 월간 실행의 소요 시간과 구독 사용량은 아직 측정하지 않았다.

항상 켜진 PC 없이 웹 버튼으로 여러 사람이 무인 실행해야 한다면, 처리량을 먼저 줄인 뒤 저비용 API를 쓰는 편이 운영상 단순하다. 로컬 모델은 외부 모델 API 비용을 없앨 수 있지만, 장비·한국어 품질·선행지표 판정 성능을 검증한 뒤 선택해야 한다.

## 현재 확인한 처리량

다음 숫자는 새 수집이나 AI 재평가 없이, 저장된 JSON을 직접 집계한 값이다. `기업 + URL`을 기사 식별 단위로 사용했다. 같은 URL이라도 타겟 기업이 다르면 귀속 판정이 달라지므로 합치지 않았다.

|---|---:|
| 대상 기업 | 77 |
| 수집 요청 | 716 |
| 수집 결과 | 431 |
| 투자 시그널 평가 행 | 109 |

| 전체 평가 행의 고유 기업·기사 | 85 |

기간 필터만 앞당겨도 이 스냅샷의 월간 보고서 평가 대상은 174→72행(58.6% 감소)이다. 기업·기사별로 묶으면 30개 자료가 된다. 174행 대비 읽기 단위는 82.8% 줄지만, 이는 **요금·토큰·실행시간 절감률이 아니다.** 한 기사에서 여러 지표를 판정하고 필요하면 근거를 추가로 읽어야 한다. 모델 응답의 usage가 성공 결과에 보존되지 않아 실제 청구액은 현재 파일로 계산할 수 없다.

`latest_ai_summary_summary.json`의 `terra_retry_count=38`은 투자 행만 집계한다. 사업동향까지 합치면 최종 Terra 결과가 69행이다. 실패한 상위 모델 호출이나 빈 응답 재시도까지 포함한 정확한 API 호출 횟수는 이 숫자로 알 수 없다.

## 병목의 원인

1. **보고서에 들어갈 수 없는 행도 먼저 평가한다.** 수집기는 상세 본문에서 날짜를 보완한 뒤 기간 필터를 다시 적용하지 않는다. 요약기도 보고서 기간을 받지 않는다. PDF 생성기에서야 기간 밖·게시일 미상 행을 제외한다. 웹 탐색 자료로 보존할 수는 있지만, 월간 보고서용 AI 작업에는 미리 제외할 수 있다.
2. **기사보다 분류 행이 작업 단위다.** 요약기의 캐시 키에 시그널 번호와 사업동향 구분이 들어간다. 같은 기사를 여러 지표와 사업동향에 대해 다시 읽는다. 기업·기사 단위에서 사실을 한 번 추출하고 각 지표 판정을 배열로 돌려주면 중복 입력을 줄일 수 있다. 서로 다른 지표 판정을 하나로 뭉개서는 안 된다.
3. **탈락 자료에도 완성된 한·영 문안을 만든다.** 현재 프롬프트는 `signal_supported=false`인 행에도 두 언어의 요약을 요구한다. 먼저 짧은 근거와 채택 여부를 결정하고, 보고서에 쓸 항목만 문안화하면 출력량을 줄일 수 있다. 현재 웹은 탈락 행의 AI 요약도 보여주므로, 미선정 자료를 원문·탈락 사유로 표시하는 소비자 변경이 함께 필요하다.
4. **문체·길이 문제도 상위 모델 재호출을 유발한다.** 사업동향 한국어 요약은 최소 220자 규칙 등이 있다. 의미 판정과 표현 수정을 분리하면 단순 분량 부족 때문에 본문 판정을 다시 할 필요가 없다. 스키마의 합성 가능한 `summary`와 `headline/detail` 중복 출력도 줄일 수 있다.
5. **근거는 길게 수집하고 앞부분만 전달한다.** 본문은 최대 24,000자지만 AI 입력은 메타데이터·근거 문구를 합쳐 기본 3,600자로 잘린다. 짧게 줄이는 것만으로 해결되지 않는다. 사건 문장과 전후 문맥을 먼저 제시하고, 기업 귀속·날짜·기술 연계가 불명확할 때 원문을 더 읽어야 한다.
6. **캐시가 있지만 역할이 묶여 있다.** 판정과 문체 프롬프트가 같은 결과 캐시에 묶여 있어 문안 규칙 변경도 재판정으로 이어진다. 사실·판정과 최종 문안을 분리해 저장하는 편이 낫다. 최신 캐시 적중 0건의 정확한 원인은 이 스냅샷만으로 확정하지 않았다.

수집 쪽에는 `official_feeds` 설정이 비어 있다. 현재는 공식 HTML 페이지와 뉴스 폴백 중심이다. 안정적인 공식 RSS가 확인되는 기업부터 교체할 수 있지만, RSS 전환 자체가 의미 판정을 대신하지는 않는다.

## 권장 운영 구조

```text
사용자: “2026년 8월 보고서 만들어줘”
  → 기존 수집기 실행 또는 해당 월 수집본 재사용
  → 보고서 기간 확인, 기업·기사 중복 정리
  → Codex가 원문을 직접 읽고 기업별로 지표·근거 판정 저장
  → 채택 항목의 한·영 문안 작성
  → 기존 게시 전 검증과 PDF 생성기 실행
  → 검토용 PDF와 미확인 항목 전달
```

JSON은 시스템 내부 데이터로 유지한다. 사용자가 생성·복사·업로드할 필요가 없다. 수십 개 기사를 한 번의 거대한 응답에 모두 넣을 필요도 없다. 기업별로 읽고 파일에 저장하면 끊긴 지점부터 이어갈 수 있다.

Codex CLI의 비대화형 실행은 저장된 인증을 재사용하며 `--output-schema`와 `-o`로 구조화된 결과를 파일에 저장할 수 있다. 로컬 Codex 앱에서도 이 프로젝트의 파일을 직접 편집하고 기존 명령을 실행할 수 있다. 구독 로그인 방식과 API 키 방식은 비용 경로가 다르다. 개인 로그인 정보를 GitHub 저장소나 공유 워크플로로 복사하는 방식은 제안하지 않는다.

현재 `validate_report_inputs.mjs`는 투자·사업동향 입력의 모든 행에 두 언어 요약과 판정 필드를 요구한다. 따라서 “일부만 평가”하도록 바꿀 때는 원본 수집 자료와 보고서 후보 입력을 구분하고 검증기·PDF·대시보드의 입력 범위를 함께 맞춰야 한다. 검증을 끄거나 미평가를 승인으로 채워서는 안 된다. 증거, 타겟 기술, 관련성 면제 기업, 선행성·사건 단계 규칙을 유지한다.

## 대안 비교

| 방식 | 모델 비용 | 사용 흐름 | 판단 |
|---|---|---|---|
| Codex 구독으로 로컬 작업 | 포함 사용량 내 별도 API 과금 없음; 구독료·한도 존재 | 월간 작업 한 번 지시, 파일 직접 저장 | 현재 내부 월간 업무에 우선 추천 |
| 로컬 모델 | 외부 모델 API 과금 없음; 장비·전력·운영 비용 | 켜진 장비에서 자동 처리 | 한국어와 의미 판정 품질을 먼저 비교 |
| 처리량 축소 + API | 토큰 종량제 | 공유 웹 버튼·서버 무인 실행 | PC 의존성을 없애야 하면 추천 |
| 키워드·템플릿만 사용 | 모델 비용 없음 | 완전 자동 | 출처 목록·발췌 브리핑은 가능. 현재의 의미 판정을 대체한다고 볼 수 없음 |

Ollama는 로컬 모델에 JSON Schema를 적용하는 구조화 출력을 지원한다. 이것은 형식 안정성 기능이며 사실성이나 선행지표 판단의 정확도를 보장하지 않는다. 이 장비에서 로컬 모델 추론은 실행하지 않았고, 모델과 메모리 요구량도 선정하지 않았다.

API 방식을 남길 경우 우선순위는 기간 필터 → 기사 단위 통합 판정 → 채택 문안만 생성 → 문체 재시도 축소 → 비용 계측이다. 입력·출력 토큰, 캐시 적중, 실제 시도 횟수와 재시도 사유를 기록해야 월 비용을 산정할 수 있다. 기다려도 되는 월간 업무에는 Batch API의 표준 동기 API 대비 50% 할인과 최대 24시간 처리 창도 검토할 수 있다. 사용할 모델의 Batch 지원 여부는 적용 시 확인해야 한다.

## 기존 수동 경로의 누락

- `.github/workflows/prepare-report-brief.yml:101`은 존재하지 않는 `scripts/build_report_brief.mjs`를 실행한다.
- `.github/workflows/build-report-from-brief.yml:34`는 존재하지 않는 `scripts/merge_summary_batches.mjs`를 실행한다.

현재 커밋에서 해당 단계에 도달하면 실행이 실패한다. 정적 파일 확인으로 확정한 누락이며 GitHub Actions를 실제 실행한 결과는 아니다. 복사·붙여넣기 흐름을 유지하지 않는다면 그 경로를 먼저 복원하기보다 파일을 직접 다루는 로컬 운영 경로를 완성하는 편이 목적에 맞는다.

## 다음 구현 범위와 검증

첫 구현은 새 서버나 오케스트레이터 없이 기존 수집·검증·PDF 코드를 재사용하는 로컬 월간 경로로 한정한다. 보고서 월을 확정하고 원본을 보존한 채 후보 입력을 준비한다. 기업·기사 단위로 판정하되 원문 근거와 지표별 결론을 유지하고, 완료된 결과는 재사용한다. PDF는 임시 출력으로 만든 뒤 기존 렌더링 도구로 한·영 레이아웃과 출처를 확인한다.

현재 스냅샷의 30개 기간 내 기업·기사를 첫 비교 대상으로 삼을 수 있다. 기존 AI 판정은 정답표로 취급하지 않는다. 실제 원문과 대조해 기업 귀속, 타겟 기술, 선행성, 미확인 사유와 최종 문안을 검토해야 한다. 이 30개는 기존 수집·키워드 필터가 남긴 후보일 뿐이므로, 77개사 전체의 수집 누락률이나 재현율을 증명하지 않는다.

이번에 완료한 것은 저장소 복제, 코드·워크플로·저장 데이터 조사, 처리량 집계와 아래 기존 검증이다. 제품 코드 수정, 새 크롤링, 유료 모델 API 호출, 로컬 모델 평가, 새 PDF 생성, 원격 배포는 수행하지 않았다.

- `node --test`: 기존 15개 테스트 통과.
- `node scripts/validate_report_inputs.mjs`: 174행의 현재 입력 계약 검사 통과.
- 위 통과는 구조·논리 일관성에 관한 것이며 기사 사실이나 모델 판정 정확도 보증이 아니다.
